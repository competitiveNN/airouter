Task: regenerate the fallback chains in ./config.yaml from the freshly fetched
free-model list in /tmp/free-models.json (output of fetch-free-models.py).
Read /tmp/free-models.json and ./config.yaml before editing anything.

When you are done, run `python3 scripts/check-rules.py`. It enforces rules 3-11
and 12 below against the fetched model list (key-group completeness, terminator,
vision/score sync, the wire shape, no dead or invented ids); the nightly sync
restores the previous config if it reports anything. Do not hand-verify instead
of running it.

Offline or fixture-driven regeneration: set SKIP_AUTO_PROBE=1 so the fetcher
touches no network and leaves existing verdicts alone. The generator then reads
both routers as unprobed, which keeps kilocode and cannot detect an outage —
and check-rules.py will flag any chain whose comment still claims a live probe,
so an offline run cannot leave a claim the data does not support.

Rules:

1. The `providers:` section stays unchanged. Only rewrite the `models:` section.

2. Map the JSON "provider" field to config providers:
   - nvidia-nim      -> nvidia, nvidia2 or nvidia3 (see rule 3)
   - kilocode        -> kilocode
   - opencode        -> opencode
   - ollama-cloud    -> ollama
   - google-ai-studio -> google
   - commandcode      -> commandcode or commandcode2 (see rule 3)

   3. Use all three NVIDIA API keys for every NVIDIA model, and both CommandCode
     API keys for every CommandCode model. Any nvidia-nim model placed in a chain
     is emitted as three consecutive entries with providers nvidia, nvidia2, nvidia3
     (same model id), and any commandcode model is emitted as two consecutive
     entries with providers commandcode, commandcode2 (same model id), so a
     rate-limited key falls through to the next key on the same model instead of
     failing the request. Preserve best-first ordering: for each model in score
     order, emit its full provider group (nvidia/nvidia2/nvidia3 trio or
     commandcode/commandcode2 pair) before moving to the next model. No nvidia-nim
     model should ever appear on only one NVIDIA provider, and no commandcode model
     should ever appear on only one CommandCode provider.

     CommandCode models are the four free-tier deals published at
     https://commandcode.ai/docs/resources/pricing-limits, fetched from the
     provider models endpoint at https://api.commandcode.ai/provider/v1/models
     (the full catalog is returned there with no free flag, so the free set is
     intersected against the curated deal list):
       stealth/space-bunny-alpha, poolside/laguna-s-2.1-free,
       inclusionai/ling-3.0-flash-sante:free, meituan/longcat-2.0-free
     The endpoint spells one of them as "meituan/LongCat-2.0" (no -free suffix,
     mixed case); canonicalize it to "meituan/longcat-2.0-free" before matching.
     Do NOT apply the generic stealth/* exclusion to commandcode models —
     stealth/space-bunny-alpha is a legitimate free deal, not an opaque
     placeholder. The stealth/* exclusion still applies to all other providers.

 4. Order each chain best-first, descending by "intelligence". Skip models whose
    intelligence is null — EXCEPT the two auto-fallback models in rule 6, which
    are always allowed regardless. Note: "intelligence" may come from two sources
    in the JSON — the Artificial Analysis intelligence index, or (when AA has no
    score) a normalized ELO from the arena.ai code leaderboard
    (https://arena.ai/leaderboard/code), exposed as the raw "elo" field. Treat
    "intelligence" as the single sortable score regardless of its source.

5. Profile selection (a model may appear in several profiles when it fits, but
   never twice in the same chain except the nvidia/nvidia2/nvidia3 trio).
   The `models:` section must contain EXACTLY these four keys and no others:
   `smart`, `work`, `fast`, `large`. The gateway's LogicalModels is
   [smart work fast large]; any other key (e.g. a `test` profile) is accepted
   by the YAML parser but is permanently unroutable, because
   /v1/chat/completions rejects it with "Unknown model". Do not add one.
   - smart: strongest generalists, intelligence >= 25, any context length.
   - work:  coding workhorses: the same pool as smart, extended down to
     intelligence >= 15. The tiny-model drop (intelligence < 15) is NOT waived
     for dedicated code models, so cohere/north-mini-code (9.9) stays out of
     `work`; it qualifies only through `large` (256,000 ctx).
   - fast:  small/cheap models only: intelligence < 25, or ids containing
     flash-lite / lightning / nano / gemma / lfm / laguna-xs. Cap at 10
     DISTINCT MODELS, counted before the nvidia trio / commandcode pair
     expansion, so the rendered chain can be longer than 10 entries.
   - large: context_length >= 200000 only. Sort by context_length desc, then
     intelligence desc.

6. The LAST entry of EVERY chain is that profile's auto fallback. It must be an
   endpoint that can actually be called — never a model that 403s. The choice
   is made on a PROBE VERDICT, never on a count:
   - preferred = `opencode`/`big-pickle` only when the chain contains opencode
     endpoints and no kilocode ones; otherwise `kilocode`/`kilo-auto/free`.
   - `fetch-free-models.py --probe-auto` records a verdict per router in the
     model list (`verified`): true = a real 1-token completion came back,
     false = the provider REFUSED the call (4xx), absent = no verdict (not
     probed, or the probe hit a 429/5xx/timeout).
   - a verdict older than 7 days (AUTO_PROBE_MAX_AGE_DAYS) counts as no
     verdict, and so does a `verified` with no `auto_probe.checked_at` — a
     `live` that old is evidence the router existed, not that it works now,
     and a fetcher that stops running must not pin the terminator forever.
   - live OR no verdict -> use the preferred router. A missing verdict is
     absence of evidence, not evidence of absence, so an unprobed, stale or
     unreachable router must never move the terminator or block a sync.
   - refused -> use the OTHER router, which is always available as a rescue
     (so one degenerate chain cannot strand the other three), and ONLY if it
     probed live. If nothing probed live, do not write the file at all: leave
     config.yaml as it is and say why. A refused terminator fails every
     exhausted request, so regenerating anyway would replace a working config
     with a worse one.
   - trailing comment records the choice, e.g.
     `# last: kilocode (auto router probed live; opencode auto not entitled to
     free tier)` or `# last: opencode (kilocode auto router probed dead)`.
     scripts/check-rules.py compares that comment against the probe record, so
     do not reword it by hand.
   - a run that CANNOT obtain a verdict (no keys, SKIP_AUTO_PROBE=1, a stale
     record, an offline fixture) must leave that comment exactly as it found
     it. Do not "correct" a `probed live` you cannot verify into `not probed`:
     the claim becomes unverifiable, not false, and check-rules.py reports
     unverifiable separately from contradictory. A changed endpoint or a fresh
     verdict is the only reason to write a new comment.


   Do NOT use a kilocode-vs-opencode count comparison to choose this. The
   opencode key authenticates but is not entitled to the free tier: 11 of its
   12 models return 403 FreeTierError (paid `big-pickle` included, re-probed
   2026-09-30). Choosing `opencode`/`big-pickle` here once made the last-resort
   endpoint of the `smart` chain a guaranteed failure.

   Only models that survived verification in fetch-free-models.py appear in
   /tmp/free-models.json, so anything in that file is callable — the point is
   to not re-add a model you know is dead. A `probe_only` record (a router the
   provider does not advertise as free) carries a verdict and nothing else: it
   is never a chain candidate.

  7. Vision capability: for every concrete (non-auto) endpoint you place in a
     chain, look up its source record in /tmp/free-models.json (same provider
     mapping + model id you already use) and read `capabilities.vision`. Emit a
     `vision:` line on that endpoint: `vision: true` when truthy, `vision: false`
     when falsy. This drives capability-aware routing (vision requests are sent
     only to vision-capable models; text-only models are skipped for them). The
     trailing auto-fallback model (kilo-auto/free / big-pickle) is a gateway
     meta-router, so emit `vision: true` for it. For a manually-added model with
     no matching JSON record, keep any existing `vision:` value as-is. Place the
     `vision:` line directly under the `model:` line (the trailing score comment
     stays on the model line), e.g.:
        - provider: nvidia
          model: moonshotai/kimi-k3  # 59.7
          vision: false

  8. Never invent model ids: only use ids present in /tmp/free-models.json.
   Never include: stealth/*, anything matching *content-safety*, or
   x-preview-f-free.

  9. Preserve the existing YAML style: `provider:` / `model:` lines with aligned
    trailing comments carrying the score, and `floor` for a model whose score is
    the synthetic smart-floor default rather than a benchmark. The context
    window is a real `context_length:` field, NOT part of the comment (it is
    what /v1/models advertises), so:
        - provider: nvidia
          model: z-ai/glm-5.3  # 44.8  elo=1623
          vision: false
          intelligence: 44.8
          context_length: 131072
    When a model also carries an "elo" field in the JSON (arena.ai code
    leaderboard), append it to the comment (`# 44.8  elo=1623`). Update the
    header comment block if the distribution rules above changed relative to
    what it describes.

  10. Self-check after editing: every profile has a non-empty chain, every
      referenced provider exists in `providers:`, the last entry of each chain is
      the auto model chosen per rule 6, every concrete endpoint carries a
      `vision:` boolean (true/false), every nvidia-nim model id appears on
      all three providers nvidia / nvidia2 / nvidia3, and every commandcode model
      id appears on both providers commandcode / commandcode2. Finish with a compact
      summary table listing the four chains (profile, entry count, head model,
      tail auto model).

  11. Every concrete endpoint must also carry an `intelligence:` field with its
      numeric score, on its own line after `vision:`. The gateway reads this at
      runtime to rotate the first endpoint chosen for a new session across the
      top `preferences.initial_rotation_window` entries of the chain, so a
      missing score silently removes an endpoint from rotation. The auto-fallback
      meta-router carries no score (it is a router, not a model) and must be left
      without the field. Keep the trailing comment score and the `intelligence:`
      field in sync.

  12. Emit `protocol: responses` on an endpoint whose record says it answered on
      /responses. OpenCode's catalog is mixed within one provider, measured live
      2026-10-02 against one key with identical gate headers:

          muse-spark-1.3-contributor-free   /chat/completions 400
                                            /responses        200
          muse-spark-1.2-contributor-free   /chat/completions 400
                                            /responses        200
          big-pickle                        /chat/completions 200
                                            /responses        400

      The refusal identifies the SHAPE, not the model. `fetch-free-models.py`
      records the protocol that answered as `protocol` on the model record;
      regenerate_config.py writes it (and only when it is not `chat`, which is
      the default and needs no line). Rules for the field:

      - NEVER emit `protocol: chat`. Absence already means chat; writing it on
        every endpoint would bury the two that actually need the field.
      - An endpoint whose record carries NO protocol keeps whatever the current
        config.yaml already declares for it. This is not optional: the generator
        owns the whole `models:` section, so a field it cannot re-emit is a field
        it deletes — a hand-written `protocol: responses` used to disappear on
        the next nightly sync, and the model went back to answering 400 on
        /chat/completions afterwards. Never re-emit a value you cannot vouch
        for; preserve the one that is there.
      - Never invent it. An unprobed record has no verdict, and absence is the
        only honest value. The router recovers at runtime by flipping and
        retrying the same endpoint (api.go), so a missing field costs one wasted
        round trip per process start — annoying, not fatal. Inventing a wrong one
        costs a real failure on every request.
      - check-rules.py rule 12 compares the field against the record that proved
        it, so do not reword or hand-tune it.
